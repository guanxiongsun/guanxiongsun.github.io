In one paragraph

Video detectors enhance each frame with features from other frames, but sliding windows and memory queues attend to everything they store and evict whole frames at a time. MAMBA’s memory bank samples a light-weight key set for each read and updates memory feature by feature, so it keeps knowledge from the whole video at a fraction of the cost. It aggregates pixel-level and instance-level features through one generalized enhancement operation (GEO).

The problem

A detector that looks at one frame at a time struggles exactly where video is hardest: motion blur, occlusion, objects caught in a rare pose. State-of-the-art video detectors therefore enhance the current frame with features from other frames, using attention over a memory. That memory is either a sliding window of nearby frames or a memory queue of recent ones.

Both structures carry two implied operations, and the paper argues that neither is efficient or sufficient:

  1. Concatenating all features in memory for enhancement. The current frame attends to everything stored, so the cost of every read grows with the memory.
  2. Frame-wise updating. When a new frame arrives, every feature of the oldest frame is deleted at once, so the memory only ever holds a short, recent slice of the video.

One way to see why: adjacent frames are often near-duplicates, so a key set that uses everything is large without being very informative, since much of it repeats nearby frames. And because whole frames are evicted, whatever the rest of the video could have told the detector is gone by the time a hard frame needs it.

The idea

MAMBA changes both operations: read a small random sample of the memory, and write feature by feature, replacing single features at random instead of whole frames. The toy below runs both memories side by side on the same 96-frame video. Watch the coverage strips: they show which frames of the video each memory still holds.

Press Play, step, or drag the frame slider. The queue’s coverage stays a tight cluster just behind the playhead; MAMBA’s spreads across the whole video. It even holds frames the video has not reached yet (the hollow ticks), because its memory was seeded from reference frames spread over the whole video. Drag to the last frame to see what each memory has kept. Then change how many keys MAMBA reads: the cost of a read follows that number, not the size of the memory.

How to read this

A toy with 48 slots and 4 features per frame; sizes are illustrative, the rules are not. They mirror vfe.pytorch’s MemoryBank: reads return everything while fewer than K features are stored and a random K-subset after that; once full, writes keep a random subset of the old features and append the new one. The released configuration holds about 20,000 RoI features (it appends until it reaches 20,000, so one update can overshoot), samples 2,000 for each read, writes each frame’s top-75 enhanced RoI features, and attends with 16 heads over 1,024-d features. Once the bank is full, a frame’s 300 proposals therefore attend to 300 × 2,000 = 0.6 M key pairs instead of 300 × 20,000 = 6 M, which is 10× fewer. The toy keeps the write ratio: MAMBA writes 1 of a frame’s 4 features, as 75 of 300 proposals. Its default K = 8 reads a sixth of a full bank, where the released model reads a tenth. The memory is seeded from 14 frames spread over the whole video; the toy seeds one feature from each, where the released code seeds each reference frame’s top-75 RoI features. In the released evaluation, frames after the first are processed in shuffled order; the toy plays them in order for readability. The diagram shows each memory as the current frame reads it, before that frame writes. Numbers here are counts in the toy, not results.

How it works

MAMBA keeps a memory bank for each video and touches it in exactly two ways, both visible in the authors’ method animation (Fig. 3).

Read: light-weight key-set construction. The current frame does not attend to the whole bank. It draws a random key set and attends only to that, so the cost of a read is set by the key-set size, not by how much the bank holds. Write: fine-grained, feature-wise updating. After a frame has been enhanced, its best features go back into the bank; once the bank is full, random individual features make room for them. The bank therefore becomes a thinned-out sample of the whole video rather than a copy of its last few frames.

In the released code, the memory is primed from the first frame of each video, which receives 14 reference frames spread evenly over the whole video: the top-75 RoI features of those frames, together with the first frame’s own, seed the bank. Every later frame reads a sampled key set and writes back its top-75 enhanced RoI features. The memory resets for each video.

GEO. A detector’s features live at two levels: pixel-level feature maps and instance-level proposals. MAMBA keeps memory at both and enhances both with one generalized enhancement operation (GEO), which aggregates multi-level features in a unified way: features of the current frame attend to a sampled key set, and what they gather is added back to them.

Implementation note

vfe.pytorch implements the instance-level (RoI) memory: two aggregators, one after each shared FC of the box head, each with 16 attention heads over 1,024-d features.

Key idea

Read a sample, write a feature.

Where it led

  1. 2021MAMBAsampled reads, feature-wise writes
  2. 2022TDViTtemporally dilated attention
  3. 2023STPNprompts instead of integration modules
  4. DirectionPhysical AImemory for agents that act

MAMBA started a line of work on what a video model should remember and how cheaply it can read it back. TDViT stacked temporally dilated attention blocks to reach far back in time cheaply, and STPN moved from separate integration modules to video prompts for one shared backbone. My current direction, Physical AI, asks the same question of agents that act in the physical world.

Open question

When an agent’s own actions decide what it sees next, which features should it keep? Random replacement worked for passive video; embodied memory needs a policy.

Code

The reference implementation and the released checkpoint live in vfe.pytorch, which also holds STPN. Version 2.0 is a rewrite in plain PyTorch, with nothing from mmcv or mmdet at runtime. After downloading ImageNet VID from the Hugging Face mirror and arranging it as the README describes, this evaluates the released model on one GPU:

uv venv --python 3.12 && uv sync
python -m vfe.cli.test configs/vid/mamba/mamba_r101_dc5_6x.py \
    CHECKPOINT --work-dir WORK_DIR
